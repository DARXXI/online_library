# Как это сделано — разбор для студентов

Этот файл — не про "что такое библиотека", а про то, **как устроен код** и что в нём
повторять руками, а что нет. Если ООП только начали проходить — читай медленно,
по разделам, не всё сразу.

## 1. Что тут вообще за технологии

- **Windows Forms** — окна, кнопки, таблицы (то, что видит пользователь).
- **MS Access (.accdb)** — файл, где физически лежат данные (как Excel, но с таблицами и связями).
- **Entity Framework Core (EF Core) + LINQ** — библиотека, которая даёт писать
  `context.Books.ToList()` вместо `SELECT * FROM Books`. Она сама превращает твой
  C#-код в SQL-запрос к Access.

Без EF Core пришлось бы писать SQL-строки руками (`"INSERT INTO Books (...) VALUES (...)"`)
и вручную читать результат построчно. С EF Core это делает библиотека — ты работаешь
с обычными C#-объектами (`Book`, `Reader`), а не со строками текста SQL.

## 2. Что писать руками, а что — нет (важно!)

В проекте у каждой формы по два файла:
```
BookListForm.cs            ← ЭТО логика: что происходит по клику на кнопку
BookListForm.Designer.cs   ← ЭТО расположение кнопок/таблицы на форме (координаты, размеры)
```

**`*.Designer.cs` и `*.resx` — не читать и не писать руками.** Это файлы, которые в
норме создаёт сама Visual Studio, когда ты перетаскиваешь кнопку мышкой в дизайнере
формы (режим "Design" — переключается вкладкой наверху редактора формы). Там просто
координаты: `new Point(150, 15)`, `Size(250, 23)` и так далее. Разбираться в них —
трата времени, которое надо потратить на логику. У меня в этом проекте нет
возможности "перетащить мышкой", поэтому Designer-файлы написаны текстом вручную —
но твоя задача **открыть форму в дизайнере VS и просто посмотреть/поправить
расположение мышкой**, а не копировать координаты глазами из файла.

Это специально: кнопки, их позиция на экране, цвет — не экзамен по ООП. Это рисуется
визуально за 2 минуты. Экономь время на этом, трать его на то, что ниже.

**Что писать/понимать руками обязательно:**
```
Models/            — классы данных (Book, Reader, Loan)
Data/               — подключение к БД
Repositories/       — как данные читаются/сохраняются
Forms/*.cs          — что происходит по кнопкам (НЕ Designer.cs, а просто .cs)
```

## 3. Что такое "контекст" (DbContext)

`LibraryContext` — это единственный класс, который знает, как достать данные из
Access-файла. Он не хранит данные сам — он **переводчик** между C# и базой:

```csharp
public class LibraryContext : DbContext
{
    public DbSet<Book> Books => Set<Book>();
    public DbSet<Reader> Readers => Set<Reader>();
    public DbSet<Loan> Loans => Set<Loan>();

    protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
    {
        optionsBuilder.UseJetOleDb(DbHelper.ConnectionString); // ← вот тут говорим, где файл .accdb
    }
}
```

`DbSet<Book>` — это как "ссылка на таблицу Books". Когда пишешь
`context.Books.ToList()`, EF Core сам:
1. открывает файл `Library.accdb`,
2. выполняет `SELECT * FROM Books`,
3. превращает каждую строку результата в объект `Book` (C#-класс),
4. закрывает файл.

Всё это одной строчкой — без EF Core это были бы 15-20 строк ручного кода на каждую таблицу.

**Контекст нужно создавать ненадолго и выбрасывать** (`using (var context = new LibraryContext()) { ... }`),
а не держать один на всё приложение — иначе он "запоминает" все когда-либо
загруженные записи, и если попробовать загрузить одну и ту же запись дважды в разных
видах — EF Core ругнётся на конфликт. Больше про это знать не нужно, просто
придерживайся схемы "открыл — сделал — закрыл", она уже так и сделана.

## 4. Repository\<T> — один класс на все три таблицы

```csharp
public class Repository<T> where T : class
{
    public List<T> GetAll() { ... context.Set<T>().ToList(); ... }
    public void Add(T entity) { ... context.Set<T>().Add(entity); context.SaveChanges(); ... }
    public void Update(T entity) { ... context.Set<T>().Update(entity); context.SaveChanges(); ... }
    public void Delete(int id) { ... найти по id, Remove, SaveChanges ... }
}
```

`T` — это "заглушка" под любой тип. Используется так:
```csharp
var bookRepository = new Repository<Book>();      // работает с таблицей Books
var readerRepository = new Repository<Reader>();   // тот же класс, но с Readers
```

Один написанный класс — работает для книг, читателей, выдач и вообще для любой
будущей таблицы. Это и называется **Generic Repository** (обобщённый репозиторий) —
стандартный паттерн, не что-то придуманное для этого проекта.

`SaveChanges()` — единственная строчка, которая реально идёт в базу и что-то меняет.
`Add()`/`Update()`/`Remove()` без неё только **помечают**, что нужно сделать — ничего
не происходит, пока не вызван `SaveChanges()`.

## 5. Как связаны формы между собой

```
MainForm  →  BookListForm  →  BookEditForm
(меню)       (список+кнопки)   (окно ввода одной записи)
```

Ключевой момент, который обычно непонятен: **как данные из маленького окна попадают
в список**. Разбор на примере кнопки "Добавить":

```csharp
// BookListForm.cs
using (var form = new BookEditForm())          // 1. создали окно ввода
{
    if (form.ShowDialog(this) != DialogResult.OK) return;   // 2. СТОП — ждём, пока закроют окно
    repository.Add(form.Book);                  // 4. читаем результат и сохраняем
    LoadBooks();                                 // 5. перезагружаем список из базы
}
```

`ShowDialog()` — не просто "открыть окно". Строка кода **останавливается** на этом
месте и не идёт дальше, пока пользователь не закроет диалоговое окно (в отличие от
`Show()`, после которого код сразу бежит дальше). Это называется **модальное окно**.

Пока окно открыто, пользователь внутри `BookEditForm` заполняет поля и жмёт
"Сохранить":
```csharp
// BookEditForm.cs
private void BtnSave_Click(object sender, EventArgs e)
{
    if (!Validate(...)) return;                  // 3а. проверка полей
    Book = new Book { Title = ..., Author = ... }; // 3б. собрали объект из полей формы
    DialogResult = DialogResult.OK;                // 3в. это "будит" ShowDialog() в BookListForm
    Close();
}
```

`Book` — публичное свойство формы (`public Book Book { get; private set; }`). Это
единственный "канал связи" между двумя формами: `BookEditForm` кладёт туда результат,
`BookListForm` его оттуда читает (`form.Book`) сразу после того, как `ShowDialog()`
разблокировался. Никакой другой магии нет — просто свойство обычного C#-объекта.

## 6. Полный путь "Добавить книгу" одним списком

1. Клик "Добавить" → `BookListForm.BtnAdd_Click`.
2. `new BookEditForm()` — пустая форма, `Book == null`.
3. `ShowDialog()` — показывает окно и ждёт.
4. Пользователь жмёт "Сохранить" → `BookEditForm` проверяет поля, создаёт `Book`,
   кладёт в своё свойство `Book`, закрывается с `DialogResult.OK`.
5. `ShowDialog()` в `BookListForm` разблокируется, возвращает `DialogResult.OK`.
6. `repository.Add(form.Book)` — передали объект в репозиторий.
7. Внутри `Add()`: `context.Set<Book>().Add(entity)` (пометили "надо вставить"),
   `context.SaveChanges()` (вот тут реально ушёл `INSERT` в Access, Access выдал новый Id).
8. `LoadBooks()` — список не "дополняется", а **грузится заново целиком** из базы —
   поэтому в таблице видно новую книгу с уже настоящим Id.

## 7. Как повторить для своей темы

1. Придумать 3 таблицы (главная / связанная / таблица-связка), минимум 5 полей
   в каждой, с текстом/числом/датой — см. общее ТЗ.
2. Создать `.accdb` и таблицы — см. `README.md`, раздел про структуру БД (там же —
   почему разрядность Access Database Engine должна совпадать с разрядностью проекта,
   если будет ошибка "provider is not registered").
3. Скопировать подход: `Models/` (простые классы-свойства) → `LibraryContext`
   (`DbSet<T>` на каждую таблицу) → `Repository<T>` (без изменений, он уже универсальный)
   → `Forms/` (список + форма ввода на каждую сущность, по образцу Book/Reader).
4. Все Designer.cs-файлы — не копировать текстом, а сделать в дизайнере VS мышкой.

## 8. Связанные вопросы, которые разбирали по ходу (коротко)

- **`Set<Book>()` vs `.Books`** — одно и то же, `.Books` это просто
  `Set<Book>()`, обёрнутый в удобное свойство. `Set<T>()` нужен там, где тип
  неизвестен заранее (внутри generic-класса `Repository<T>`).
- **DI (Dependency Injection) тут не используется** — осознанно. DI решает проблему
  "подменить реализацию" (тесты, разные БД), которой в учебном проекте из 3 таблиц
  нет. Через DI пришлось бы объяснять ещё и контейнер, scope, `CurrentValues.SetValues`
  — лишняя сложность без пользы. Как это выглядело бы — см. историю правок.
- **Интерфейсы (`IRepository<T>`) тоже не нужны** — они нужны, только когда
  реализаций больше одной (или для тестов). У `Repository<T>` реализация всегда одна.
